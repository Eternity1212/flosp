## 1. 要回答的问题

Messidor-2 外测 QWK 的 seed 间 SD 实测 **0.033**（台账 §8）。
我们一直把它当作"训练随机性"。但模型选择是在约 100 轮上对验证 `macro_qwk`
取 **argmax**，而实测最佳轮散布在 **37 / 53 / 60 / 77 / 99** ——
对"平台期均匀分布"的 KS 检验 **p = 0.982**，即 argmax 基本是在平台上随机选。
验证集不大（IDRiD 仅 103 张，单轮噪声约 0.049；四中心 macro 后仍有 **0.02** 量级）。

在含 0.02 噪声的平坦曲线上、从 100 个候选里取 argmax，是典型的 winner's curse。

**于是：0.033 里有多少来自"选哪一轮"，而不是"训得怎样"？**

$$\mathrm{Var}_{\text{total}} = \underbrace{\mathrm{Var}_{\text{选择}}}_{\text{run 内、窗口各轮之间}} + \underbrace{\mathrm{Var}_{\text{训练}}}_{\text{run 之间、窗口均值的差异}}$$

这是本项目里**唯一还可能产出方法贡献**的方向（台账 §12.4），
而且它几乎不花钱：11.8 GPU·h / 10 run。

## 2. 实验（已固定，不再改动）

配置文件 `configs/variance_decomposition.csv`：

| exp_id | 策略 | seed | extra_args | est_gpu_h |
|---|---|---|---|---:|
| `diag_varsel_fedavg` | fedavg | 3;4;5;6;7 | `--no-fsr --no-shallow-proto --no-deep-proto --eval-external-every 5` | 5.7 |
| `diag_varsel_fedproto` | fedproto | 3;4;5;6;7 | `--no-fsr --proto-agg sample --eval-external-every 5` | 6.1 |

- **seed 3–7**，取自从未参与过组件筛选的干净区间 3–12。
- **两个方法**，用来检验"选择方差占比"是否依方法而异。
- `extra_args` 与 `experiment_matrix.csv` 的 `base_fedavg` / `base_fedproto`
  **逐字相同**，只多一个 `--eval-external-every 5`。
- 成本估法：`base_fedavg` 3.3 GPU·h ÷ 3 seed = 1.1/run，
  `base_fedproto` 3.5 ÷ 3 = 1.17/run，外测开销 **+4%**，各 ×5 seed。

```bash
python scripts/scheduler.py --matrix configs/variance_decomposition.csv \
       --stage bench --gpus 0,1,2,3 --jobs-per-gpu 2
python scripts/variance_decomposition.py --prefix diag_varsel --metric ext_qwk
```

## 3. 分析规程（预先固定）

| 项 | 取值 | 备注 |
|---|---|---|
| 主指标 | `ext_qwk`（Messidor-2 未见中心 QWK） | 与主端点一致 |
| 统计窗口 | **后 50% 采样点**，固定 | `variance_decomposition.window_start`，无可调阈值 |
| 选择方差 | 窗口内各轮的 run 内方差（合并各 run 的 SS/df） | |
| 训练方差 | 各 run 窗口均值之间的方差（ddof=1） | |
| 占比定义 | $\mathrm{Var}_{\text{选择}}/(\mathrm{Var}_{\text{选择}}+\mathrm{Var}_{\text{训练}})$ | |
| 辅助指标 | `ext_referable_auroc` | 只作一致性参考，**不参与判定** |

**窗口为什么固定而不自动检测平台**：作者先后写过三版自动平台检测，
每一版都在合成数据上被找出系统性偏差，而且**全都朝同一个方向**
（截短窗口 → 低估 run 内方差 → 把结论推向"训练主导"，
也就是把一个可能成立的方法贡献误判成阴性）。详见
`scripts/variance_decomposition.py::window_start` 的 docstring 与 README。
收敛速度差异改由 Spearman 趋势检验**显式报出**，不藏在自动判定里。

## 4. ★ 判定规则（二值，**看到结果之前已固定**）

| 选择占总方差 | 结论 | 后续动作 |
|---:|---|---|
| **> 60%** | **支持方法贡献**：选择噪声是主要矛盾 | 修选择规则（窗口内权重平均 / 平滑后取 argmax / SWA），并用同一套 seed 复测 |
| **< 30%** | **噪声不可约**，这是更强的阴性结论 | 写进基准论文，不再尝试选择规则类改动 |
| 30%–60% | 两者相当 | **两个都报**，不得只挑一边写 |

### 4.1 纪律条款

1. **60% 与 30% 这两个阈值不得在看到任何结果之后修改。**
2. 不得因为"差一点就到 60%"而换指标、换窗口、加 seed 再判一次。
   要加 seed 必须**在本文件里先登记新的 n 和新的判据**。
3. 两臂（fedavg / fedproto）若落在不同档位，**如实报"占比依方法而异"**，
   不得只取对自己有利的那一臂。
4. 无论落在哪一档都写进论文。**不存在"白跑"** —— 这正是预先固定判据的意义。

### 4.2 为什么必须写在前面

本项目已经有一次现成的教训（台账 §4.1）：同一个配置、三次估计
**+0.0220 / +0.0443 / +0.0290**，相差近一倍。在 σ_d≈0.027 的噪声下，
事后挑阈值可以把几乎任何结果说成想要的样子。
台账 §11 记录的 12 个实现缺陷里有 8 个是**静默失败**；
事后改判据是同一类问题的统计学版本 —— 不报错，只是安静地产出想要的结论。

## 5. 预先登记的失效情形

下面几种情况**不算**支持方法贡献，出现时须照实报告：

| 情况 | 怎么发现 | 判定 |
|---|---|---|
| 窗口内仍有显著趋势（未收敛） | 脚本输出的 Spearman 趋势 p < 0.05 | run 内方差混了趋势项，**高估**选择方差；须换更靠后的窗口复算并同时报出两个结果 |
| argmax 选中轮并不优于窗口均值 | 脚本输出的 `lift < 0.002` | 这是 winner's curse 的**正面证据**，但仍按 §4 的占比判定，不另立结论 |
| 有效 run 少于 4 个 | 脚本报"有效数据不足" | 不出结论，补跑到 5 个 run 再判 |
| 两臂占比差 > 20 个百分点 | 两次运行脚本对比 | 结论只能按方法分别陈述，不得合并成一个数 |
